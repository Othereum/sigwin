# presage gotchas (learned the hard way)

- `Manager` futures are `!Send`: everything runs on the backend thread's `LocalSet` (`spawn_local`). Box large futures (`Box::pin`).
- Received and sent messages are saved by presage itself, but a sent one only after every recipient was sent to (groups: one encrypted copy per member device, one request per member; no sender keys / multi-recipient endpoint). The vendored `libsignal-service` patch (see `vendor/PATCHES.md`) sends to up to `GROUP_SEND_CONCURRENCY` (16) members at once. The log prints `group send done ms=…`. Until the save, `App.pending` shows a stub row (`pending_row`, status "전송 중"/"실패"); `Internal::Sent(ts, …)` drops it and reloads the window. The send timestamp is fixed up front and is the message id. If any member's send fails, presage returns the error and doesn't save, though others may already have the message: a failed row may be partly delivered, and retrying keeps the timestamp so recipients drop the copy (Desktop by sender + sent timestamp). Rate limits are waited out inside the send queue (`send_job`). Failed rows live only in memory (`App.pending`).
- **Receipts are filed under the sender's 1:1 thread**, never the group. Status therefore comes from our `ls_receipts(target_ts, who, level)` table: filled live in `content()`, backfilled once (`Persist.receipts_indexed`). Look statuses up by the content's sent timestamp (`ContentExt::timestamp`).
- **Display order is `ls_order.seq`, not `ts`.** `ts` is the sender's clock (and still the message id); `seq` is the stored order, assigned by triggers on presage's `thread_messages` (`db::ensure_order`), so the window isn't sorted by `ts` and a `ts` range doesn't describe it. A sent message is stored when its send ends, so it lands after what arrived meanwhile; sends per thread are queued (`send_turn`) to keep our own in order. A presage migration rebuilding `thread_messages` drops the triggers: `Index::open` restores them and fills the gaps.
- `store.messages(thread, range)` does `fetch_all`: always bound the range (use `Index::page` first, then `fetch_range`, which falls back to single reads when one wrong clock stretches the range).
- presage doesn't send delivery receipts. We batch them per sender in `pending_receipts`. Read receipts go out (plus one `SyncMessage.read` to our devices) for incoming messages in the open window while focused (not in the background, not away: `away.rs`, the backend's `focused` means the user is working in the window) and showing the thread's newest messages (`App::sees_latest`; `queue_reads`, flushed with the delivery batch). A thread opened with unread messages isn't read as a whole: the list lands on the first unread one (`Open.divider`, found by counting `persist.unread` incoming rows from the newest) and `ReadUpTo` reads as rows come fully on screen (`read_through`; the UI holds it back while a jump settles); `Persist.read_upto` is the per-thread watermark, advanced by read syncs from the phone too, and a thread without one only counts its `unread` messages (no flood of receipts for old history). The phone's `Configuration.read_receipts` off suppresses the receipts but not the sync.
- DB key is passed as a raw key `"x'<hex>'"`: a passphrase would trigger sqlcipher's PBKDF2 (seconds per connection). Keep `disable_statement_logging()`, otherwise sqlx logs the key; `sqlx` log level is `error`.
- **Session state is read-modify-write across awaits.** libsignal has no lock of its own, so anything loading then saving a session must hold `cipher::SESSION_LOCK` (vendor patch) and must not hold it across the network. Overlapping tasks don't fail where they overlap: the peer fails to read a later message.
- `install_sticker_pack` also syncs the pack to the user's phone. Don't call it in tests.
- **Disappearing messages:** presage fills `expire_timer` on every outgoing `DataMessage` from the stored thread timer (`restore_thread_timer`), so leave it `None` when sending. It never deletes expired messages: `App::sweep` does (per-thread progress in `Persist.sweep`), and `view::build` hides expired rows right away. The timer runs from the send time (we don't track reads).
- Received deletes for everyone are applied by presage (target replaced by a `NullMessage` with a nil sender). Which deleted rows were ours comes from `ls_deleted_mine` (filled when our delete is sent or synced from our phone) or a missing `server_guid` (presage-sent rows have none). Edits are stored as `EditMessage`s and folded in `view::build` (author must match). Our own reactions, edits and deletes are `App.ops`, shown optimistically until `Internal::Sent`.
- **Pinned messages:** presage stores `PinMessage`/`UnpinMessage` data messages but keeps no pin state. Ours is `ls_pins` (thread key, target sent ts), filled live in `content()` via `record_pin`, backfilled once (`Persist.pins_indexed`); our own pins are written when sending and undone if the send fails. `load_pins` (every `emit_messages`) drops expired pins, pins of deleted messages and everything past `MAX_PINS`. A pin may be outside the window, so its edited text can't come from `view::build`'s folding: `ls_edits` says where the author's newest edit is stored. That's the row's metadata timestamp; `ContentExt::timestamp` of an edit is its target's. Jumping moves the window to the target if it isn't close (`App::jump_to`); the UI then homes in on the row (`jump_to_row`): a ListView only instantiates rows on screen and rescales all positions after every layout, so it alternates measure / move frames and seeks with the ListView's own formula; `stick_to_bottom` stays off meanwhile.
- **The window can be anywhere in the thread.** `Open.end_seq` is `Some` when it stops short of the newest message: new messages then don't join it, and code assuming it ends at the newest (stub rows, reloads, typing) must check. Bound every read by it, never `rows_from` alone.
- **The window holds only rows that show (`Open.window`).** A 1:1 thread is mostly receipts: its newest 600 rows can hold no message at all, so anything that counts rows in `ls_order` says nothing about messages, and a read of a seq range there can be far larger than the window (`reload_window` reads the window's own rows plus what's new).
- **What changes a message is stored after it, outside the window.** Reactions come from `ls_reactions` and edits through `ls_edits` (`view::Indexed`). Rows of an edit have their target's `ContentExt::timestamp` but no row of their own.
- **Thread list previews (`refresh_snippet`):** a receipt moves a 1:1 thread's last row, so it looks only at rows since the cached one, and re-reads the cached message for its edits. A delete for everyone replaces its target in place without moving the last row, hence `forget_snippet`.
- **presage fetches link previews by itself:** `send_message` / `send_message_to_group` contact the first link of any outgoing `DataMessage` whose `preview` is empty, directly, with no switch, blocking the send and logging the url on failure. `send_task` therefore always sets `preview` for a body with a link (`backend::linkpreview::for_message`): ours or `no_preview`, whose `url` must be present even if empty, because Signal iOS drops a whole message whose preview has no url field. Any new way of sending a body needs the same.
- Typing indicators: presage can't send "online only", so offline devices get them late; we drop stale incoming ones and skip sending in groups over `TYPING_MAX_GROUP` (one send per member). Group typing messages carry the group *identifier* (`group_identifier`), not the master key.
- **Our `ls_*` tables outlive builds** (installed apps auto-update and keep their DB; `CREATE TABLE IF NOT EXISTS` doesn't touch an existing table). New table: just add its `CREATE`. Changing an existing one: leave its `CREATE` alone, add a `db::step` and bump `db::SCHEMA`; for rebuildable tables (receipts, pins, edits, packs, stickers) prefer drop + recreate + re-run the backfill. `ls_deleted_mine` can't be rebuilt: carry its data over.
